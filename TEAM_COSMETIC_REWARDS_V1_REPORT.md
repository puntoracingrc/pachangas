## Authoritative bridge

The bridge is an `AFTER INSERT` trigger on canonical
`pachanga_achievement_grants`. It accepts only active team grants generated by
an active V3 definition and resolves the canonical progression fact, mapping,
catalog item, team, eligible admins and revisions entirely on the server.

Idempotency is enforced by deterministic operation IDs, advisory transaction
locks, a private reward ledger and unique constraints over policy, mapping,
team and canonical grant. Replays return the stored canonical response. A team
that already owns a mapped item records `already_owned`; it receives no second
copy, points, currency, compensation or personal reward box.

The private grant, policy and trigger functions have no execution permission for
`public`, `anon` or `authenticated`. The private policy, mapping, event and
ledger tables have RLS enabled and no client grants.

## Activation and non-retroactivity

The migration installs policy version 1 in `ready` state. Activation is a
separate idempotent private operation that records `effective_from` and a
monotonic `effective_from_server_sequence` frontier before enabling
`team_cosmetic_rewards_enabled`.

Facts at or before that frontier are ignored. There is no backfill query or
history scanner. Disabling the flag stops future cosmetic grants while the
canonical achievement engine continues normally. Later sporting corrections
do not confiscate a cosmetic that was already revealed and granted; its source
evidence remains immutable in the private ledger.

## Inventory, NEW and notifications

- The reward is written directly to team inventory and is never auto-equipped.
- Each owner/admin eligible at acquisition receives one idempotent notification.
- The deep link opens `/equipo/identidad` with the unlocked cosmetic category.
- Seen state remains per admin; one admin cannot clear another admin's `NEW`.
- An admin appointed later does not receive historical `NEW` state.
- Members receive a sanitized team snapshot and no private inventory rows.
- The public shield read model changes cosmetically only after an admin equips and saves the item.
- Realtime invalidates inventory and shield state; clients refetch the canonical snapshot.

No new client write exists for granting. The PWA bridge therefore needs no new
write classification and cannot present a server reward as an offline success.
