# Pachangas IQ database bootstrap V1

## Supported histories

The repository deliberately supports two database histories without rewriting migrations already applied in existing environments.

### Fresh local Supabase database

```bash
supabase start
PACHANGAS_BOOTSTRAP_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55322/postgres npm run db:bootstrap:fresh
supabase migration list --local
```

The command:

1. accepts loopback PostgreSQL URLs only;
2. verifies that the requested host, port and database match the selected local Supabase workdir;
3. compares the complete migration filename set and SHA-256 of every file with the selected workdir;
4. verifies the immutable baseline SHA-256 in `supabase/baselines/manifest.json`;
5. refuses any database that already contains Pachangas product relations;
6. applies the baseline through `20260731080738` in one transaction;
7. records the 36 absorbed migration versions with the local Supabase CLI;
8. applies every migration from `20260803053357` onward through `supabase migration up`;
9. verifies the complete migration ledger and rejects a leaked `simulation` schema.

The command is intentionally not a general reset command. Re-running it against a populated database returns `BOOTSTRAP_PRODUCT_DATABASE_NOT_EMPTY` before any mutation.

### Existing database

```bash
supabase migration list --local
supabase migration up --local --include-all
supabase migration list --local
```

Existing environments keep their original migration ledger. They do not apply the fresh-install baseline and receive only migrations absent from their ledger.

## Baseline maintenance

- `supabase/baselines/20260731080738_pachangas_product_baseline.sql` is immutable.
- Migrations 1-36 remain in `supabase/migrations` as deployed history and audit evidence.
- New product changes always use a new forward migration.
- A future squash requires a new baseline version and a new manifest; never replace this baseline in place.
- `simulation/`, generated worlds and laboratory schemas are never product migration inputs.

## Schema comparison

Export the normalized local contract with:

```bash
PACHANGAS_SCHEMA_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55322/postgres npm run db:schema-contract > /tmp/pachangas-schema.json
```

The contract includes relations, columns, constraints, indexes, RLS flags, policies, function bodies and signatures, triggers, schema/table/function ACLs and Realtime publication membership.

## Recovery rehearsal

This is a local disaster-recovery check, not a production command. Refuse any non-loopback database URL and never run it against a linked project.

1. Export the normalized schema contract and selected fixture fingerprint before backup.
2. Archive product objects and data separately from Auth identities:

```bash
pg_dump -Fc --no-owner \
  --schema=public --schema=private --schema=supabase_migrations \
  "$SOURCE_DATABASE_URL" > /tmp/pachangas-product.dump

pg_dump -Fc --data-only --table=auth.users \
  "$SOURCE_DATABASE_URL" > /tmp/pachangas-auth-users.dump
```

3. Stop only the disposable project, delete only its registered Docker volume, initialize a new empty local Supabase platform, and verify that it contains zero Pachangas product relations.
4. Restore Auth identities. Drop only the empty product schemas generated by the platform and restore the product archive without `--clean`.
5. Generate a reviewed `pg_restore --list` file and exclude only `DEFAULT ACL` entries owned by managed roles such as `supabase_admin`. Do not omit explicit schema, table or function ACLs.
6. Restore the product archive with `--exit-on-error`, recreate the exact `supabase_realtime` table membership captured in the pre-backup contract, and normalize only ACL owner representations shown to differ by the contract comparison.
7. Re-export the schema contract and fixture fingerprint. Recovery fails unless both hashes match byte for byte, all migration ledger rows are present, Auth users are restored and an authenticated canonical read succeeds.

Do not use `--clean` when restoring a schema-scoped archive into an empty platform: archive pre-data can attempt to drop policies before their target relations exist. Do not treat a zero `pg_restore` exit as sufficient; schema ACLs and publication membership are part of the product contract and must also match.

The V1 rehearsal restored three Auth users, all 80 migration ledger rows, the exact schema SHA-256 `4a2f278293329560e1b202d81080222b8a5077b346757f8885fe866fbeefcc34` and the exact fixture SHA-256 `9a790a5893cc04f8ba9174bc9a7ff99cab14bff18f94748c874784cc41a69da8` after deleting the isolated database volume.
